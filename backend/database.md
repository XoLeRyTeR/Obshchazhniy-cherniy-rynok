# Схема базы данных

[Диаграмма классов с полями и кратностями связей](database-classes.md).

Реализованы 8 моделей SQLAlchemy 2.0, асинхронное подключение, 21 метод FastAPI и начальная миграция Alembic. Миграция проверена на отдельной локальной PostgreSQL 17. Импорт `src.models` регистрирует таблицы в `Base.metadata`, но сам по себе ничего не создаёт. Инструкции — [README.md](README.md).

## Таблицы

| Модель / таблица | Поля и назначение |
|---|---|
| `University` / `universities` | UUID `id`, `name` до 200 символов, вычисляемый `name_key`. Справочник вузов |
| `Dormitory` / `dormitories` | UUID `id`, FK `university_id`, `name` до 80, вычисляемый `name_key`. Одно общежитие принадлежит одному вузу |
| `User` / `users` | UUID `id`, уникальный `email` до 254, `password_hash`, `name` до 80, FK `dormitory_id`, `created_at`. Вуз определяется через общежитие |
| `Listing` / `listings` | UUID `id`, FK `owner_id`/`dormitory_id`, `title` до 120, `description` до 5000, `category`, `format`, `price`, `status`, `created_at`, `updated_at` |
| `ListingPhoto` / `listing_photos` | UUID `id`, FK `listing_id`, уникальный `storage_key`, `position` 0–4. В БД нет бинарных изображений и абсолютных путей |
| `Chat` / `chats` | UUID `id`, FK `listing_id`/`buyer_id`, `created_at`. Автор определяется через объявление, второй участник — buyer |
| `Message` / `messages` | UUID `id`, FK `chat_id`/`sender_id`, `text` до 4000, UUID `client_message_id`, `created_at` |
| `ChatRead` / `chat_reads` | Составной PK `(chat_id, user_id)`, FK `last_read_message_id` вместе с `chat_id`. Строка появляется после первого прочтения; отсутствие строки означает, что сообщения ещё не читались |

Все поля обязательны. Первичные UUID генерируются Python при вставке или PostgreSQL через `gen_random_uuid()` для прямой SQL-вставки. Требуется PostgreSQL 13+; для нового развёртывания следует выбрать поддерживаемую серверную версию. Все даты — `TIMESTAMPTZ`, серверный default — `now()`. Объект Python до flush может ещё не иметь ID/дат/статуса: это defaults вставки.

Число и название общежития хранятся одной строкой. `name_key` вычисляет PostgreSQL: схлопывает пробелы, обрезает края, приводит к нижнему регистру. Это защищает уникальность и при прямом SQL. Отображаемое `name` сервис нормализует до сохранения. Ключ не передаётся клиентом и не заполняется вручную. Сравнение регистра опирается на locale PostgreSQL; рабочая и тестовая базы должны иметь одинаковую UTF-8 locale с поддержкой кириллицы. Для upsert используется уникальная пара `(university_id, name_key)`.

Email хранится нормализованным; CHECK запрещает ненормализованное значение, UNIQUE запрещает дубликат. Проверка полноценного формата email и хеширование пароля относятся к схемам/сервису. Вход выдаёт один JWT access-токен, в БД токены не хранятся. Выход — удаление токена на устройстве; повторный вход выдаёт новый. Сервер проверяет подпись и срок токена; существование пользователя проверяется независимо от таблицы токенов.

## Ограничения и индексы

- Формат: sell/give/exchange/service; статус: active/reserved/completed/archived; категория: books/electronics/furniture/clothes/dishes/food/other. Python использует перечисления, БД — VARCHAR с CHECK допустимых значений.
- Цена — целые копейки в диапазоне 0–1 000 000 000. Sell требует цену >0; give/exchange — 0; service допускает 0. Услуга не может иметь reserved/completed. Условия обмена и место встречи обсуждаются в описании или чате; отдельных столбцов для них нет.
- Пустые или состоящие только из пробельных символов обязательные тексты запрещены CHECK. Максимальная длина ограничена VARCHAR. Нормализация пользовательского текста и строгие типы JSON остаются в будущих схемах.
- UNIQUE `(listing_id, buyer_id)` защищает от двух одинаковых чатов. UNIQUE `(chat_id, sender_id, client_message_id)` обеспечивает основу повторной отправки сообщений; сравнение текста повторов выполняет сервис.
- UNIQUE `(listing_id, position)` вместе с CHECK `position BETWEEN 0 AND 4` запрещает шестое фото даже в обход API. Сервис под блокировкой объявления выбирает свободный слот; пропуски после удаления допустимы. `storage_key` — безопасное серверное имя без каталогов, например UUID с расширением jpg/png/webp. Фактические байты и размеры проверяет сервис фотографий.
- Составной FK `(last_read_message_id, chat_id)` → `messages(id, chat_id)` запрещает отметить сообщение из другого чата. Дополнительный UNIQUE `(id, chat_id)` на messages нужен как цель этого FK. Связь ORM `last_read_message` доступна только для чтения; метка записывается явными ID после проверки участника.
- Индексы покрывают выборку своих объявлений, ленту по общежитию/статусу, общую активную ленту, историю сообщений, справочники и внешние ключи. Индексы UNIQUE уже обслуживают поиск по своим левым префиксам, отдельные дубли не добавлены.

`last_activity_at`, `last_message` и `unread` чата вычисляются запросом, а не хранятся дублирующими счётчиками. Последнее сообщение выбирается через индекс `(chat_id, created_at, id)`, а при отсутствии сообщений активность равна созданию чата. Запросы нужно делать пакетно, без отдельного запроса для каждой строки списка.

## Удаление и границы ответственности

Объявления закрываются статусом. FK с RESTRICT защищают вузы, общежития, авторов, покупателей, объявления с чатами и чаты с сообщениями от физического удаления с потерей истории. Ссылки меток прочтения также запрещают удалить отмеченное сообщение. API удаления этих сущностей пока не предусмотрен.

Для служебных дочерних данных предусмотрен CASCADE: фотографии удалённого объявления без чатов, метки удалённого пользователя/пустого чата. ORM использует `passive_deletes`, чтобы применять правила БД, а не обнулять обязательные FK. Удаление строки фото не удаляет физический файл — это работа сервиса с повторной очисткой.

Внешние ключи подтверждают существование объектов, но не права пользователя. Следующие правила реализуются сервисами в транзакциях: автор меняет только своё объявление; участник читает/пишет только свой чат; нельзя писать самому себе; нельзя передать объявление другому автору; статус меняется по матрице с проверкой expected_status; метка чтения движется только вперёд.

При отправке сообщения сервис блокирует чат и назначает `created_at` строго позже последнего сообщения при равенстве или откате часов (+1 микросекунда). Это предотвращает попадание нового сообщения «до» прочитанной метки. Для чтения используется тот же порядок `(created_at, id)`. Правило реализовано в ChatService, не в ORM-модели.

`updated_at` объявления обновляется SQLAlchemy при UPDATE, но не триггером PostgreSQL. Прямой SQL должен явно обновлять поле; CHECK защищает от значения раньше created_at. Начальный статус/авторство также проверяются API, а не доверяются входящему JSON.

## Файлы и проверка

- `src/db/base.py` — Base, UUID и время создания.
- `src/models/` — по файлу на сущность; `enums.py` — коды форматов/статусов/категорий; `__init__.py` импортирует все таблицы для Alembic.
- `requirements.txt` — SQLAlchemy, asyncpg, Alembic, FastAPI, Pydantic, JWT, Argon2, Pillow и зависимости тестов.
- `tests/unit/test_models.py` — конфигурация ORM, сборка запросов со связями, PostgreSQL DDL, составной FK, уникальные ключи, enum и типы дат.

Из каталога `backend`, после установки зависимостей в своё окружение:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -W error -m unittest tests.unit.test_models -v
```

Тесты ORM/DDL не требуют БД и не заменяют проверку реальных ограничений. Дополнительно интеграционные проверки уже прошли на отдельной PostgreSQL, включая параллельные операции. Полный список расширенных проверок — в `tests/API_TEST_PLAN.md`; на сервере пользователя схема пока не создавалась.

Используемые механизмы описаны в документации SQLAlchemy: [типизированные модели](https://docs.sqlalchemy.org/en/20/orm/declarative_tables.html), [ограничения и составные FK](https://docs.sqlalchemy.org/en/20/core/constraints.html), [defaults и вычисляемые поля](https://docs.sqlalchemy.org/en/20/core/defaults.html).
