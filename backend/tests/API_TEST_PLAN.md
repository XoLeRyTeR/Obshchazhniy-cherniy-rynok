# План тестирования API

Дата: 29 октября 2026 года. Проект: «Общажный чёрный рынок».

Это полный план проверок API, подготовленный до реализации. Теперь API реализован и автоматизирован основной набор: 116 тестов и 25 вложенных проверок прошли на PostgreSQL 17. Все 21 метод охвачены; полный перечень сценариев ниже ещё не полностью автоматизирован. Фактические проверки находятся в `unit/test_models.py`, `unit/test_contracts.py`, `integration/test_api.py`, `integration/test_concurrency.py`, `integration/test_flows.py`, `integration/test_constraints.py`; ограничения покрытия перечислены в README. Полный перебор любых возможных данных невозможен: используем классы эквивалентности, границы, матрицы прав и переходов, повторные и конкурентные запросы, управляемые сбои.

## 1. Уточнения контракта

Ниже зафиксированы проектные решения для однозначного ожидаемого результата. Это план первой версии, а не описание уже работающего сервера.

- Предметные пути имеют префикс `/api/v1`; `/health` и `/ready` — вне префикса. Публичны регистрация, вход и справочники вузов/общежитий: справочники нужны до регистрации. Остальные методы требуют `Authorization: Bearer …`. Вход выдаёт один access-токен, выход выполняется его удалением на устройстве; HTTP-методов refresh/logout нет.
- Создание пользователя, объявления, фото, нового чата/сообщения — `201`. Чтение, PATCH, вход, возврат существующего чата/сообщения — `200`. Удаление фото — `204` без тела.
- `401` — недействительная авторизация. `403` — чужое действие над доступным объявлением. `404` — объект отсутствует или недоступен: приватные чаты и чужие закрытые объявления скрываются за `404`. Проверка доступа предшествует раскрытию состояния объекта.
- `409` — конфликт уникальности, статуса, лимита фото или повторного ключа сообщения. `422` — ошибка полей/сочетаний/параметров пагинации. Для фото: `413` — размер файла, `415` — неподдерживаемый формат, `422` — повреждённое изображение или недопустимые размеры. Rate limit — `429` с `Retry-After`. Неожиданный сбой — `500`; неготовность БД у `/ready` — `503`.
- Бизнес-ошибки: `{detail: {code, message}}`. Строковые `code` фиксируются при реализации схем; HTTP-статусы обязательны уже здесь. Для `422` проверяем список ошибок и поля, не точную фразу библиотеки.
- JSON должен быть объектом. Неизвестные поля запрещены (`422`), включая серверные ID, автора, отправителя, даты, role, password_hash. Цена строго целая: boolean, строка и дробь не принимаются. Неизвестные query-параметры тоже отклоняются; для GET это нужно реализовать явно.
- PATCH меняет только переданные поля; пустой объект и null для обязательного поля — `422`. Проверяется итоговое состояние после объединения с текущими данными. Ошибка одного поля отменяет весь PATCH.
- Email: trim, нижний регистр, корректный формат, максимум 254 символа. Пароль: 8–128 символов, не только пробелы; без trim и нормализации. Имя: 1–80 после trim и схлопывания повторных пробелов.
- Общежитие: либо `dormitory_id`, либо вместе `university_id` и `dormitory_name`. При регистрации выбор обязателен; в PATCH профиля можно не передавать. Смешение способов и неполная пара — `422`, отсутствующая связанная сущность — `404`. Имя 1–80 после нормализации пробелов, сравнение без регистра внутри вуза; число «17» допустимо.
- Объявление: обязательны title (1–120), description (1–5000), category, format, price. Длины после trim. Отдельных полей условий обмена и места встречи нет; детали можно указать в description или обсудить в чате. Старые поля exchange/place в JSON запрещены как неизвестные. Общежитие по умолчанию из профиля, можно выбрать другое существующее. Начальный статус — active.
- Цена в копейках: 0–1 000 000 000. Для sell минимум 1, give/exchange только 0, service допускает 0. При смене формата несовместимые поля не сбрасываются молча: клиент передаёт согласованный итог.
- Смена статуса принимает `{expected_status, status}`. Устаревшее ожидаемое состояние, переход в тот же статус и запрещённый переход — `409`; неизвестный enum — `422`.
- Сообщение: `{text, client_message_id}`; ID — UUID. Text 1–4000 после trim, внутренние переводы строк сохраняются. Повтор ключа с тем же нормализованным текстом — `200` с исходным сообщением, с другим — `409`.
- Чтение: `{last_read_message_id}`. Та же/более старая метка — успешный `200` без движения назад. Порядок определяется `(created_at, id)`, а не одним UUID.
- Фото: ровно один multipart-файл `file`, не более 5 242 880 байт и 5 фото на объявление. Статические JPEG/PNG/WebP; размеры каждой стороны 1–6000, суммарно до 20 000 000 пикселей. Проверяются декодирование и соответствие заявленного/реального формата; анимация и несовпадение формата — `415`. Пределы — исходные настройки MVP.
- Все списки: `{items}`; `offset` по умолчанию 0, допустимо 0–9223372036854775807; `size` по умолчанию 20, допустимо 1–100. Выборка начинается с `offset` и содержит не более `size` записей. Смещение за концом списка возвращает пустой `items` и `200`. Следующее смещение — `offset + items.length`; неполная/пустая страница завершает загрузку. Старые `cursor`/`limit` — неизвестные параметры, `422`. Объявления и сообщения сортируются по `(created_at, id)` убывающе, справочники — `(name_key, id)` возрастающе, чаты — `(last_activity_at, id)` убывающе. Активность — последнее сообщение или создание чата.
- На неизменных данных обход страниц не теряет/не повторяет записи. При вставках, удалениях или изменении порядка между запросами смещения могут сдвигаться: клиент обновляет список с первой страницы и объединяет по ID. Snapshot-пагинация не обещается.
- Поиск q — подстрока названия/описания без регистра после trim, максимум 200 символов; пустой q равен отсутствующему. `%` и `_` — буквальные символы, а не SQL wildcard.
- JWT содержит sub/iat/exp и случайный jti, в БД не сохраняется. Сервер проверяет подпись, срок и существование пользователя. Срок задаётся настройкой; после истечения — повторный вход. Локальный выход не отзывает сохранённую копию токена на сервере. Повторный вход выдаёт новый JWT с другим jti, не аннулируя прежний до его exp.
- Ограничитель регистрации/входа имеет настраиваемые порог и окно. Для тестов задаются небольшие значения; производственные лимиты этот план не назначает.

## 2. Фикстуры и выполнение

U1/U2 — вузы; D1/D2 принадлежат U1, D3 — U2. A — автор, B — собеседник, C — посторонний, G — гость. У A/B по два независимо выданных JWT для проверки нескольких устройств. Есть все категории, четыре формата и все допустимые статусы; чаты A–B и A–C, сообщения обоих участников. Часть записей имеет одинаковое время.

Каждая проверка: подготовить независимые данные → запрос → проверить HTTP/схему/содержимое → прочитать сохранённый результат через новый запрос или сессию БД. Для ошибок записи проверять отсутствие новых строк, файлов и токенов, а не только HTTP. Временные границы — через управляемые часы.

Гонки запускаются на отдельных соединениях PostgreSQL с барьером перед спорной операцией. SQLite и одна общая внешняя транзакция теста не подтверждают работу блокировок/commit. Тесты используют изолированную БД/схему и временный каталог фото; запуск должен отказываться от URL рабочей базы.

Одна строка может быть параметризованной семьёй: каждый перечисленный вариант выполняется отдельно. P0 — авторизация, права, целостность, цены и основные пользовательские операции. P1 — остальные границы, поиск, пагинация и сбои. Оба уровня необходимы до подключения реальных пользователей.

## 3. Общие проверки каждого подходящего метода

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| GEN-01 | Каждый закрытый метод: нет Bearer, пустой/случайный токен, другая схема авторизации | 401, запись не выполняется |
| GEN-02 | Истёкший JWT, неверная подпись, alg=none, отсутствующие/неверные sub/iat/exp/jti | 401, без внутренних деталей |
| GEN-03 | JWT указывает на удалённого/несуществующего пользователя | 401 |
| GEN-04 | UUID в path/body/query: malformed / корректный несуществующий | 422 / 404, кроме явно оговорённых фильтров |
| GEN-05 | Битый JSON, массив, пропущенное обязательное поле, неверный тип, лишнее поле | 422; неподдерживаемый content-type JSON-метода — 415 |
| GEN-06 | Подмена серверных полей в каждом методе записи | 422, авторство/ID/даты не изменены |
| GEN-07 | Каждый ответ: password/hash/SQL/внутренний путь | Не раскрываются; один access-токен только в успешных auth-ответах, email только в собственном профиле/auth |
| GEN-08 | Каждый метод записи: сбой до commit после подготовки изменений | 500, нет частичного результата, следующая операция работает |
| GEN-09 | Каждый метод чтения: неожиданный сбой БД | 500, безопасный ответ, соединение освобождено; health отдельно |
| GEN-10 | Каждый список: 0/1/20/21 запись, size 1/100, offset 0/1/за концом | Верные размер и смещение; пусто — 200; при неизменных данных нет повторов |
| GEN-11 | Size 0/−1/101/дробь/строка; offset отрицательный/дробный/строка/выше bigint; старые cursor/limit | 422 |
| GEN-12 | Одинаковый ключ сортировки, полный обход страниц | Детерминированный порядок, нет дублей/пропусков при неизменных данных |
| GEN-13 | Кириллица, emoji, апострофы, SQL-подобный текст | Обрабатываются как данные, SQL не исполняется |
| GEN-14 | GET и отказанные операции | Не меняют предметные данные; чтение истории само не отмечает прочтение |
| GEN-15 | Логи при ошибках/auth/загрузке | Нет паролей, токенов, полных тел запросов и бинарных фото |
| GEN-16 | Неизвестный URL / неподдерживаемый HTTP-метод | 404 / 405 |

Auth-проверки выполняются с валидным body/path, валидация — с действующим токеном: не закрепляем случайный порядок независимых ошибок.

## 10. Сквозные и инфраструктурные проверки

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| FLOW-01 | A регистрируется/публикует → B находит/пишет → A отвечает → B читает | Общие серверные данные у независимых аккаунтов, верный unread |
| FLOW-02 | Договорённость → A резервирует → B пытается завершить → A завершает | B получает 403; вещь скрыта из ленты после завершения, чат сохранён |
| FLOW-03 | A создаёт общежитие → B выбирает его | Одна общая запись с произвольным названием |
| FLOW-04 | Перезапуск API и повторный вход | Объявления, чаты, метки, фото сохранены |
| FLOW-05 | Локальный выход одного устройства | Его токен удалён, показан вход; второе устройство продолжает работу |
| FLOW-06 | Услуга → чат → попытка брони → архив | Бронь 409, архив разрешён |
| INFRA-01 | Миграции на чистой PostgreSQL, повтор upgrade до head | Схема создана, повтор безопасен |
| INFRA-02 | Прямое нарушение ограничений БД | Запрещены дубли email/dorm/chat/message key, отрицательная цена, неверные enum/FK, service+reserved/completed |

| INFRA-05 | Фото по выданному HTTPS-URL, попытка обхода пути media | Фото читается; выход за MEDIA_DIR невозможен |

## 11. Автоматизация и критерий готовности

Реализованы `tests/integration/test_api.py`, `test_flows.py`, `test_concurrency.py`, `test_constraints.py` и проверки `tests/unit`. Общие фикстуры — `tests/conftest.py`. Первоначальная разбивка по одному файлу на предметную область объединена в компактный test_api.py; при расширении покрытия его можно разделить.

Тесты сохраняют ID сценария из документа; перечисленные варианты становятся отдельными параметрами. UUID и время проверяются по формату/связям/допустимому диапазону либо задаются управляемыми генераторами. Для длины изображений используются настоящие валидные файлы, а не просто набор нулевых байт.

Критерий полного покрытия: все сценарии перенесены в исполняемые проверки или имеют явно описанное ограничение. Сейчас все 21 метод, основные правила и гонки проверены на PostgreSQL; расширенные отказы и нагрузка остаются в плане. TOKEN-02/03/05/06 и локальная часть FLOW-05 должны проверяться при подключении клиента. Отчёт pytest подтверждает только фактически запущенные тесты, не весь перечень этого документа.
