# Архитектура бэкенда «Общажный чёрный рынок»

Дата: 29 октября 2026 года.

Статус: реализованы 21 метод FastAPI, асинхронное подключение PostgreSQL, 8 моделей SQLAlchemy и начальная миграция Alembic. На отдельной локальной PostgreSQL 17 прошли 116 тестов и 25 вложенных проверок. Мобильный frontend подключён: регистрация, два аккаунта, переписка, фото, статусы и восстановление входа проверены браузерным сценарием. Запуск — [README.md](README.md), схема — [database.md](database.md). Развёртывание на сервере пользователя ещё не выполнено.

Сценарии проверки 21 метода и уточнения контракта до реализации: [tests/API_TEST_PLAN.md](tests/API_TEST_PLAN.md). В плане закреплены границы полей, ответы при повторах и конкуренции, коды ошибок и порядок пагинации.

## 1. Основа архитектуры

За образец взят локальный проект `D:/Projects/telesnay_krepilnya_backend/src`: разделение на `api/routers`, `api/dependencies`, `services`, `repositories`, `models`, схемы Pydantic и `db/migrations`. В нём сервисы получают `DbRepository`, который объединяет предметные репозитории с общей `AsyncSession` и предоставляет `flush`, `save`, `rollback`.

Для нашего проекта используем такой же слоистый монолит: одно приложение FastAPI и одна PostgreSQL. Основной путь запроса:

`HTTP-запрос → router → service → repository → PostgreSQL`

`Depends` собирает зависимости: сессию БД, `DbRepository`, сервис и текущего пользователя. Схемы Pydantic описывают входные и выходные данные, модели SQLAlchemy — таблицы.

Отличия от образца: каталог `schemas` пишется без опечатки; Python-файлы именуются в `snake_case`, классы — `PascalCase`. Общие настройки и ошибки находятся в `core`. Общий интерфейс `IRepository` пока не нужен: у поиска объявлений и истории сообщений разные запросы, поэтому абстракцию добавляем только при реальном повторении кода.

## 2. Границы первой версии

Бэкенд обслуживает регистрацию и вход, профиль, справочники вузов и общежитий, объявления, фотографии, поиск, личные диалоги и сообщения. Форматы объявлений: продажа, бесплатная передача, обмен и услуга.

У всех пользователей один тип аккаунта. «Автор» — пользователь, создавший конкретное объявление; «покупатель» — другой участник диалога. Это отношения между записями, а не отдельные роли. Администратора, жалоб, оплаты внутри приложения и отдельного раздела сделок нет.

Для первого API принимаем текущее поведение прототипа: автор вручную меняет статус вещи после договорённости в чате. Отдельных заявок с принятием, таблицы сделок и автоматического закрепления вещи за покупателем пока нет. Это базовое решение для реализации, а не ранее согласованный сценарий подтверждения заявки.

## 4. Ответственность реализованных слоёв

| Слой / файлы | Ответственность |
|---|---|
| `src/main.py` | Создать FastAPI, подключить роутеры и обработчики ошибок, настроить CORS и завершение работы ресурсов |
| `core/config.py`, `security.py`, `errors.py` | Настройки окружения, хеширование паролей и токены, предметные ошибки |
| `api/routers/auth.py`, `users.py`, `catalog.py`, `listings.py`, `chats.py` | Принять запрос, вызвать сервис, вернуть ответ; без SQL и бизнес-правил |
| `api/dependencies/db.py`, `services.py`, `auth.py` | Создать зависимости на запрос, проверить JWT и получить текущего пользователя |
| `db/database.py`, `base.py` | Async engine, фабрика сессий, базовый класс ORM |
| `models/` | SQLAlchemy-модели, связи, ограничения и индексы |
| `schemas/auth.py`, `users.py`, `catalog.py`, `listings.py`, `chats.py` | Pydantic-схемы запросов и ответов; наружу не отдаётся `password_hash` |
| `repositories/db_repository.py` | Репозитории с одной сессией и управление фиксацией изменений |
| `repositories/user_repository.py`, `catalog_repository.py`, `listing_repository.py`, `chat_repository.py`, `photo_repository.py` | SQL-запросы, фильтрация, сортировка, пагинация и блокировки; фотографии и защита очистки медиа — в PhotoRepository |
| `services/auth_service.py`, `user_service.py`, `catalog_service.py`, `listing_service.py`, `chat_service.py`, `photo_service.py` | Проверки прав, бизнес-правила, последовательность операций и работа с файлами |
| `tests/unit/`, `tests/integration/` | Проверки правил и проверки API с отдельной тестовой PostgreSQL |

Сервис не зависит от FastAPI и не выбрасывает `HTTPException`. Сервисы не импортируют SQLAlchemy и не обращаются к сессии или движку напрямую: запросы, удаление записей и блокировки выполняют предметные репозитории. Фиксация/откат всей операции остаётся через `DbRepository.save()`/`rollback()`. Это разделение проверяет `tests/unit/test_service_boundaries.py`. Роутер не обращается к сессии напрямую. Предметный репозиторий не решает, имеет ли пользователь право менять объявление, и самостоятельно не вызывает `commit`.

Одна бизнес-операция использует одну сессию и одну транзакцию. Сервис вызывает `DbRepository.save()` после всех изменений, при ошибке — `rollback()`. `flush()` нужен для получения созданных идентификаторов до фиксации. Dependency закрывает сессию и откатывает незавершённую транзакцию. Вложенные сервисные вызовы не фиксируют часть операции отдельно. Уникальные ограничения БД защищают от параллельных одинаковых запросов.

## 5. Данные и связи

Таблицы описаны моделями и начальной миграцией, применённой к отдельной локальной PostgreSQL:

| Таблица | Поля и связи |
|---|---|
| `universities` | `id`, `name`, уникальное нормализованное `name_key` |
| `dormitories` | `id`, `university_id`, `name`, `name_key`; уникальная пара `(university_id, name_key)` |
| `users` | `id`, уникальный нормализованный `email`, `password_hash`, `name`, `dormitory_id`, `created_at`; вуз определяется через общежитие |
| `listings` | `id`, `owner_id`, `dormitory_id`, `title`, `description`, `category`, `format`, `price`, `status`, `created_at`, `updated_at` |
| `listing_photos` | `id`, `listing_id`, серверный ключ файла, `position` |
| `chats` | `id`, `listing_id`, `buyer_id`, `created_at`; уникальная пара `(listing_id, buyer_id)`, автор берётся из объявления |
| `messages` | `id`, `chat_id`, `sender_id`, `text`, `client_message_id`, `created_at`; уникальная тройка `(chat_id, sender_id, client_message_id)` |
| `chat_reads` | `chat_id`, `user_id`, `last_read_message_id`; уникальная пара `(chat_id, user_id)` |

Идентификаторы сущностей — UUID, наружу передаются строками. Время хранится в `TIMESTAMPTZ`, API отдаёт ISO 8601 в UTC. Цена — целое количество копеек, как в текущих моках; для «Отдам» и «Обмен» равна нулю. Для продажи — положительная; для услуги допускается ноль как «по договорённости». Форматы и категории — фиксированные допустимые значения с ограничениями, отдельные CRUD-таблицы для них пока не нужны.

API использует коды формата `sell`, `give`, `exchange`, `service`. Категории: `books`, `electronics`, `furniture`, `clothes`, `dishes`, `food`, `other`. Русские подписи соответствуют текущим значениям интерфейса. Все поля API именуются в `snake_case`; при подключении клиента адаптер преобразует их в его модель. `ownerId: "me"` заменяется настоящим ID пользователя; `mine` определяется сравнением `sender_id` с ID текущего пользователя.

У объявления собственная ссылка на общежитие. Переезд автора не переносит автоматически ранее опубликованные вещи. `owner_id`, `sender_id`, начальный статус и даты определяет сервер; эти поля не принимаются как доверенные данные от клиента. Передавать право собственности на объявление в MVP нельзя.

Начальные индексы: `listings(dormitory_id, status, created_at, id)`, `listings(owner_id, created_at, id)`, `messages(chat_id, created_at, id)` и индексы внешних ключей для частых соединений. Поиск первой версии — по названию и описанию; полнотекстовый индекс добавляется при необходимости. Пагинация — `offset` (по умолчанию 0, неотрицательный) и `size` (по умолчанию 20, от 1 до 100). Сортировка объявлений и сообщений — `(created_at, id)` по убыванию, справочников — `(name_key, id)` по возрастанию, чатов — `(last_activity_at, id)` по убыванию; активность чата определяется последним сообщением или временем создания. Репозитории выполняют SQL с `ORDER BY`, `OFFSET` и `LIMIT`; сервисы не строят и не выполняют запросы страниц. При добавлении записей между запросами возможны повторы: клиент обновляет начало списка и объединяет записи по ID.

## 6. Общежития, объявления и чат

**Общежития.** Клиент получает список для выбранного вуза. При регистрации или изменении профиля передаётся либо `dormitory_id`, либо пара `university_id` и `dormitory_name`. Одновременная передача обоих вариантов отклоняется. Для нового имени убираются крайние и повторные пробелы, проверяется длина 1–80 символов, `name_key` формируется без учёта регистра. Число «17» — допустимое название. В пределах одного вуза существующая запись переиспользуется; конкурентное создание обрабатывается через уникальное ограничение и upsert. Новое общежитие и профиль сохраняются одной транзакцией. Начальные вузы загружаются отдельной seed-командой.

**Объявления.** Читать ленту могут авторизованные пользователи; менять текст, фотографии и статус — только автор. Лента по умолчанию показывает `active` и `reserved`; завершённые и архивные записи остаются доступны автору и участникам связанного чата. Объявления архивируются без удаления переписки. Географическое расстояние не вычисляется: фильтрация идёт по вузу и общежитию.

Переходы соответствуют текущим кнопкам:

| Исходный статус | Разрешённые действия автора |
|---|---|
| `active` | `reserved` для вещей; `archived` для любого формата |
| `reserved` | `active` — снять бронь; `completed` — вещь передана |
| `completed` или `archived` | `active` — опубликовать снова |

Для услуги бронь вещи не используется: автор архивирует предложение. Смену формата зарезервированной вещи на услугу сервис отклоняет, пока бронь не снята. Команда смены статуса передаёт ожидаемый исходный статус; сервер блокирует строку и проверяет его в транзакции. Если состояние уже изменилось, возвращается `409`. Покупатель не может менять статус чужой вещи.

**Чаты.** Диалог создаётся по объявлению между автором и заинтересованным пользователем. Повторное нажатие «Написать» возвращает тот же чат. Написать самому себе нельзя. Новый диалог разрешён для `active` и `reserved`; существующая переписка сохраняется после завершения или архивации. Доступ к истории, отправке и отметке прочтения имеют только два участника. Пустой текст отклоняется, предел сообщения — 4000 символов. `client_message_id` позволяет безопасно повторить отправку после сетевого сбоя. Метка прочтения может указывать только на сообщение этого чата и сдвигается только вперёд; непрочитанные считаются по сообщениям другого участника.

Для первого API сообщения отправляются и читаются по HTTP. Клиент периодически обновляет открытый чат и список диалогов. WebSocket можно добавить следующим этапом, сохранив те же сервисы и таблицы; он не является условием готовности первого бэкенда.

## 7. Реализованное API

Общий префикс — `/api/v1`. Предметные ручки требуют авторизации, кроме регистрации, входа и чтения справочников вузов/общежитий: справочники нужны для заполнения регистрации до входа. Ответы описываются схемами Pydantic и попадают в OpenAPI. Выход выполняется локально удалением токена, отдельные методы обновления токена и серверного выхода не нужны.

| Метод и путь | Действие |
|---|---|
| `POST /auth/register`, `POST /auth/login` | Регистрация / вход, выдача одного access-токена и профиля |
| `GET /users/me`, `PATCH /users/me` | Получить / изменить свой профиль |
| `GET /universities`, `GET /dormitories?university_id=…` | Справочники для профиля |
| `GET /listings` | Лента: `q`, `category`, `format`, `university_id`, `dormitory_id`, `offset`, `size` |
| `GET /users/me/listings` | Все собственные объявления с фильтром статуса |
| `POST /listings`, `GET /listings/{id}`, `PATCH /listings/{id}` | Создать, посмотреть, изменить объявление |
| `PATCH /listings/{id}/status` | Изменить статус с проверкой автора и перехода |
| `POST /listings/{id}/photos`, `DELETE /listings/{id}/photos/{photo_id}` | Добавить / удалить фото своего объявления |
| `POST /chats`, `GET /chats` | Получить или создать чат по `listing_id` / список своих диалогов |
| `GET /chats/{id}/messages`, `POST /chats/{id}/messages` | История с пагинацией / отправка сообщения |
| `PATCH /chats/{id}/read` | Обновить отметку прочтения |

Отдельно от префикса: `GET /health` проверяет работу процесса, `GET /ready` — доступность БД. Списки возвращают `{items}` без курсоров и общего количества; клиент увеличивает `offset` на число полученных записей и завершает загрузку при неполной или пустой странице. Бизнес-ошибки имеют вид `{detail: {code, message}}`; ошибки схем — стандартный ответ валидации FastAPI со статусом `422`. Основные статусы: `401` — нет действующего токена, `403` — действие запрещено, `404` — запись отсутствует или недоступна участнику, `409` — конфликт данных. Внутренняя ошибка возвращается как `500` без текста SQL или трассировки.

## 8. Авторизация, фотографии и сервер

Пароли сохраняются только в виде хеша Argon2id. При входе и регистрации выдаётся один JWT access-токен с `sub`, `iat`, `exp` и случайным `jti`, различающим повторные выдачи. Токены в БД не хранятся; dependency проверяет подпись и срок, затем получает существующего пользователя по `sub`. Таблицы сессий и refresh-механизма нет. Срок access-токена задаётся настройкой. При выходе клиент удаляет токен из памяти и постоянного хранилища и открывает вход; после истечения токена требуется повторный вход. Сохранённая копия токена действует до `exp`, серверного отзыва нет. Секреты берутся из окружения, обязательные настройки проверяются при запуске. Email и хеш пароля не попадают в публичные сведения об авторе. Вход и регистрация получают ограничение частоты запросов. Подтверждение почты и восстановление пароля — отдельный последующий этап с почтовым сервисом.

Фото передаются как `multipart/form-data`, сохраняются в постоянном каталоге сервера, а в БД хранятся ключи и порядок. API возвращает HTTPS-URL; путь из телефона или base64 в PostgreSQL не сохраняется. Начальные лимиты: 5 изображений на объявление, 5 МБ на файл; допустимы JPEG, PNG и WebP с проверкой фактического содержимого и размеров изображения. Имя файла генерирует сервер. Загрузка проверяет автора и лимит под блокировкой объявления. При неудачной записи БД новый файл удаляется; при удалении фото сначала фиксируется удаление ссылки, затем удаляется файл, а неудачи очистки повторяются отдельной командой. Отсутствие фото допустимо.

Размещение: домен с HTTPS → Nginx или Caddy → Uvicorn/FastAPI → PostgreSQL и каталог фотографий. PostgreSQL доступен только серверному приложению. Веб-превью клиента получает явно заданные CORS origins. В рабочем режиме отключены `debug` и SQL `echo`, пароли, токены и полные тела запросов не логируются.

Настройки: `DATABASE_URL` с драйвером `asyncpg`, `JWT_SECRET`, `ACCESS_TOKEN_TTL`, `CORS_ORIGINS`, `MEDIA_DIR`, `MEDIA_BASE_URL`. В репозитории есть `.env.example` без настоящих секретов. Схема БД изменяется через Alembic перед запуском новой версии, не через `create_all` при старте. Резервируются и PostgreSQL, и фотографии. Конкретный домен и параметры сервера задаются при развёртывании.

3. Выполнено: объявления, поиск, статусы и фотографии.
4. Выполнено: диалоги, история, отправка и прочтение сообщений.
5. Frontend подключён к API; два независимых аккаунта проверены браузерным прогоном и HTTP-тестами. Следующий этап — проверка на физическом Android и развёртывание на сервере пользователя.

Проверки включают права на чужие объявления и чаты, допустимые переходы статусов, одно общежитие при параллельном создании, один чат при повторном запросе, отсутствие дублей сообщений, откат всей операции при ошибке, истечение JWT и локальный выход. Интеграционные тесты используют отдельную PostgreSQL с применёнными миграциями. Тестовая база не совпадает с рабочей.

Двухпользовательский сценарий проверен интеграционными тестами: публикация, переписка, прочтение, бронь и завершение. Дополнительные сценарии отказов/нагрузки перечислены в README и тест-плане; их выполнение на стенде остаётся отдельным этапом.
