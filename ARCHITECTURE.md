# Обзор архитектуры

«Общажный чёрный рынок» — студенческий маркетплейс для продажи, передачи, обмена вещей и предложения услуг. Пользователи публикуют объявления, ищут предложения по вузу и общежитию и договариваются в личном чате.

Обновляйте этот обзор при изменении границ слоёв, модели данных, контракта API или схемы развёртывания.

## 2. Общая схема системы

```text
Пользователь ↔ Expo Go (Android) / браузер
                          ↕ HTTP API /api/v1, фотографии /media
                  Uvicorn / FastAPI
                          ├──↔ PostgreSQL
                          └──↔ Каталог фотографий
```

Клиент передаёт запросы в FastAPI. Роутер валидирует входные данные через Pydantic и вызывает сервис. Сервис проверяет права и бизнес-правила, обращается к репозиториям и фиксирует изменения. PostgreSQL хранит сущности и связи, а API принимает изображения отдельными multipart-запросами и отдаёт их из каталога медиа.

## 3. Основные компоненты

### 3.1. Клиентское приложение

**Назначение.** Регистрация и вход, лента с поиском и фильтрами, просмотр и редактирование объявлений, загрузка фотографий, профиль и личные чаты. После входа доступны вкладки «Главная», «Чаты» и «Профиль».

**Технологии.** React Native, React, TypeScript, Expo SDK 57, Expo Router и React Native Web. Проект использует Feature-Sliced Design. Зависимости направлены от `app` к `pages`, `features`, `entities` и `shared`. Слайсы экспортируют публичный интерфейс через `index.ts`, а точечные связи между сущностями оформлены через `@x`. Стили находятся рядом с компонентами в `styles.ts` и `*.styles.ts`.

**Состояние.** `SessionProvider` хранит сессию и профиль, `ListingProvider` — объявления, `ChatProvider` — переписку. При смене аккаунта приватные кеши пересоздаются. Открытая переписка обновляется каждые 3 секунды, список диалогов — каждые 4 секунды, пока соответствующий экран активен.

**Запуск.** Android через Expo Go, браузерное превью через Metro. Клиент обращается к API на порту 8000 по адресу браузера или Expo LAN, если `EXPO_PUBLIC_API_URL` не задан явно. [Инструкция по запуску](README.md)

### 3.2. Серверное приложение

**Назначение.** Один FastAPI-сервис обслуживает сессии и профили, справочники вузов и общежитий, объявления и фотографии, чаты и отметки прочтения. Точка входа — `backend/src/main.py`, фабрика `create_app`.

**Технологии.** Python 3.12, FastAPI, Pydantic, SQLAlchemy 2, asyncpg, Alembic, Pillow и Uvicorn. SQL-запросы, фильтрация, сортировка и блокировки находятся в репозиториях. Сервисы управляют фиксацией и откатом операции через `DbRepository`.

**Правила.** Лента доступна авторизованным пользователям и показывает объявления со статусами `active` и `reserved`. Поддерживаются форматы `sell`, `give`, `exchange` и `service`. Бронь хранится как статус вещи. При смене статуса сервер проверяет автора, переход и `expected_status`. Услуги можно архивировать и снова публиковать. Для пары «объявление и заинтересованный пользователь» создаётся один чат. Повтор отправки с тем же `client_message_id` возвращает исходное сообщение.

**Контракт.** Основной префикс — `/api/v1`, Swagger UI — `/docs`. Списки принимают `offset` и `size` и возвращают `{items}`. Клиент увеличивает смещение на число полученных записей и прекращает загрузку на неполной или пустой странице.

**Размещение.** API работает локально. Целевая схема собственного сервера описана в разделе 6. [Архитектура бэкенда и методы API](backend/architecture.md)

## 4. Хранилища данных

### 4.1. PostgreSQL

Основная база приложения. Alembic управляет схемой, модели SQLAlchemy расположены в `backend/src/models/`.

| Таблицы | Данные |
| --- | --- |
| `universities`, `dormitories` | Вузы и их общежития |
| `users` | Профили, нормализованная почта, хеш пароля и ссылка на общежитие |
| `listings` | Объявления, автор, общежитие, формат, категория, цена и статус |
| `listing_photos` | Ключи и порядок фотографий объявления |
| `chats`, `messages`, `chat_reads` | Диалоги, история переписки и отметки прочтения |

Идентификаторы сущностей — UUID. Цена хранится целым числом копеек. Общежитие объявления хранится отдельно от текущего общежития автора. [Схема базы](backend/database.md)

### 4.2. Файловое хранилище фотографий

Изображения хранятся в постоянном каталоге `MEDIA_DIR`. API отдаёт файлы через `/media` и строит ссылки по `MEDIA_BASE_URL`. Сервер проверяет содержимое JPEG, PNG и WebP и принимает до пяти файлов на объявление по 5 МиБ каждый. Команда `python -m src.manage cleanup-media` удаляет файлы, на которые больше нет ссылок в БД.

### 4.3. Локальное хранилище сессии

На Android JWT хранится в Expo SecureStore. Браузерное превью использует AsyncStorage поверх localStorage. При запуске клиент проверяет токен через `GET /api/v1/users/me`. Ответ `401` или выход из аккаунта очищает сохранённый токен и завершает сессию.

## 5. Внешние интеграции и API

Все пользовательские сценарии обращаются к собственному HTTP API проекта. Expo Go используется для запуска приложения на Android. Вузы и общежития поступают из справочников PostgreSQL. Текущий MVP работает без сторонних сервисов для платежей, карт, рассылок и push-уведомлений.

## 6. Развёртывание и инфраструктура

- **Текущее окружение.** Локальные Expo/Metro, Uvicorn и PostgreSQL. Серверное развёртывание по HTTPS остаётся в плане.
- **Целевая схема.** Собственный сервер с публичным IP и HTTPS-доменом. Nginx или Caddy принимает внешний трафик и передаёт его Uvicorn/FastAPI. PostgreSQL доступна приложению по локальному или внутреннему адресу. Для восстановления нужны резервные копии БД и каталога фотографий.
- **Конфигурация.** Сервер читает переменные из окружения, образец находится в `backend/.env.example`. Перед запуском применяются миграции Alembic. Для рабочего окружения задаются домен медиа, разрешённые источники CORS и `SEED_DEMO_DATA=false`.
- **CI/CD.** Команды проверок и миграций описаны в README клиента и сервера. Конфигурации CI/CD в репозитории нет.
- **Мониторинг.** `GET /health` проверяет процесс API, `GET /ready` проверяет соединение с БД с таймаутом. Бэкенд использует стандартный `logging` Python.

## 7. Безопасность

- **Аутентификация.** Регистрация и вход выдают один JWT HS256, который клиент передаёт как `Authorization: Bearer …`. Пароли хешируются Argon2id. Срок действия токена задаёт `ACCESS_TOKEN_TTL`. Выход удаляет токен на клиенте, а ранее выданная копия действует до истечения срока.
- **Авторизация.** Публичны вход, регистрация и чтение справочников. Сервер проверяет токен для пользовательских операций, разрешает менять объявление и фотографии только автору и открывает переписку только участникам чата. Файлы по `/media` доступны по публичным URL, в том числе после архивации объявления.
- **Секреты и транспорт.** `JWT_SECRET` и `DATABASE_URL` задаются на сервере. Для внешнего доступа предусмотрен HTTPS на reverse proxy. Для браузера разрешённые источники задаёт `CORS_ORIGINS`.
- **Защита запросов.** Вход и регистрация ограничены по частоте в каждом процессе API. Для нескольких workers общий лимит настраивается на reverse proxy. Ошибки API скрывают содержимое секретных полей и внутренние исключения.

## 8. Разработка и тестирование

1. Создайте окружение Python в `backend/`, установите зависимости из `requirements.txt` и настройте `backend/.env` по образцу.
2. Поднимите PostgreSQL, примените `python -m alembic upgrade head` и при необходимости заполните справочник командой `python -m src.manage seed-universities "ИГЭУ"`. Запустите `python -m uvicorn src.main:create_app --factory --host 0.0.0.0 --port 8000` из `backend/` для доступа с телефона по LAN.
3. В корне проекта установите зависимости через `npm install` и выполните `npm start` для Expo Go или `npm run web` для браузера.

| Что проверяется | Команда и инструменты |
| --- | --- |
| Типы клиента и тестов | `npm run typecheck`, TypeScript |
| Модели, HTTP-клиент, границы слоёв и стили | `npm test`, встроенный раннер Node.js |
| Бэкенд и границы серверных слоёв | `python -m pytest tests/unit -q` из `backend/` |
| API, PostgreSQL, транзакции и конкурентные операции | `python -m pytest -q` из `backend/` с `TEST_DATABASE_URL` отдельной БД с суффиксом `_test` |
| Соответствие моделей и миграций | `python -m alembic check` из `backend/` |
| Сквозной сценарий с двумя аккаунтами | `node scripts/check-ui.cjs` с Playwright и работающими клиентом и API |

Параметры запуска и требования к тестовым базам описаны в документации. [Клиент](README.md) · [Бэкенд](backend/README.md) · [План проверок API](backend/tests/API_TEST_PLAN.md)

## 9. Дальнейшее развитие

- Развернуть API по HTTPS на собственном сервере и проверить резервное копирование и восстановление PostgreSQL и фотографий.
- Проверить сквозные сценарии на физическом Android. Для отдельной сборки добавить совместимые пакеты `expo-secure-store` и `expo-crypto` и настроить их нативное подключение.
- Добавить подтверждение почты и восстановление пароля с почтовой интеграцией. Подтверждение статуса студента требует отдельного механизма.
- При необходимости ускорить обновление чатов через WebSocket, сохранив сервисы и таблицы сообщений.
