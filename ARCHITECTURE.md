# Общажный чёрный рынок — архитектура MVP

Актуальный отдельный план бэкенда и его каркас от 29 октября 2026 года: [backend/architecture.md](backend/architecture.md). Для серверной части он имеет приоритет над предварительными предложениями ниже, включая заявки и WebSocket.

Актуальная схема содержит 8 таблиц: вход с одним JWT без хранения токенов в БД, выход удалением токена на устройстве. В объявлении нет отдельных полей условий обмена и места встречи; формат «Обмен» сохранён. Состав реализованных моделей — в [backend/database.md](backend/database.md).

Обновлено: 29 октября 2026 года. Frontend подключён к FastAPI и локальной PostgreSQL; двухпользовательский сценарий проверен в браузере. Серверное развёртывание ещё не выполнено. Последующие разделы содержат исходные предложения; актуальные реализованные решения — в README и документации backend.
Подтверждено пользователем: Android с Expo Go; клиент React Native; backend Python + FastAPI и PostgreSQL на собственном сервере с публичным IP, доступ к API по домену через HTTPS. Supabase исключён.
Остальные технические детали ниже — предложения. Подтверждение брони автором объявления пока НЕ согласовано: это предложенный вариант, а не исходное требование пользователя.

## Текущий frontend

Стили хранятся в соседних `styles.ts`/`*.styles.ts`, а не внутри TSX: рядом с каждым экраном, карточкой и набором общих компонентов. Динамические стили также определены в этих файлах. Корневой layout и вкладки вынесены в `pages/layout/ui` вместе со стилями; `src/app/_layout.tsx` и `src/app/(tabs)/_layout.tsx` остаются адаптерами Expo Router без дополнительных маршрутов для файлов стилей. Автотест запрещает возвращать inline-стили в компоненты.

Expo-приложение использует API для регистрации/входа, профиля, справочников, поиска, публикаций, фотографий и чатов. Моковые аккаунты и объявления удалены. На Android сохраняется только JWT в SecureStore, в браузерном preview — в AsyncStorage/localStorage; пароли не сохраняются. Повторный запуск получает профиль из /users/me, ответ 401 удаляет токен и открывает вход.

Frontend перенесён на Feature-Sliced Design: `src/app` — только маршруты и композиция провайдеров Expo Router; `pages` — экраны; `features` — сохранение объявлений/фото, смена статуса и отправка сообщений; `entities` — пользователь, объявление, чат и местоположение; `shared` — HTTP, платформа, общий UI и утилиты. Состояние разделено между SessionProvider, ListingProvider и ChatProvider; при смене пользователя приватные кеши пересоздаются. Импорты идут вниз по слоям через публичные index.ts, связи сущностей описаны в @x. Это проверяется tests/architecture.test.ts. Старые общие store/model и файлы всех экранов удалены. Сторонние библиотеки кеша/форм не добавлены; детали — в README.

Автор меняет статус через API из объявления или чата; сервер проверяет права и expected_status. Списки/сообщения приходят с сервера; открытый чат обновляется каждые 3 секунды, список диалогов — каждые 4. История загружается страницами, повтор сообщения использует прежний client_message_id. Отдельных сделок и блока бронирований в профиле нет.

Вузы и общежития загружаются из публичных справочников API. Пункт «В списке нет моего общежития» открывает произвольное название/номер; backend нормализует и сохраняет его. Поведение одинаково при регистрации и редактировании профиля.

Фотографии отправляются multipart-файлами и хранятся на сервере; без фото используется заглушка. Если после сохранения объявления загрузка фото не удалась, форма сохраняет полученный ID и повторяет операции для той же записи. Отдельных exchange/place больше нет; детали обмена/встречи описываются текстом. Скелетоны показывают реальную загрузку, ошибки требуют повтора. Восстановление пароля и отправка почты пока не реализованы.

## 1. Границы проекта

Студенты публикуют объявления четырёх типов: «Продам», «Отдам», «Обмен», «Услуга». Другие пользователи находят объявления, общаются и договариваются о передаче вещи или выполнении услуги.

В MVP входят регистрация, вход, лента, поиск и фильтры, просмотр объявления, публикация и редактирование своих объявлений, фотографии, личные чаты, заявки/бронирования и профиль.

Администратора и жалоб нет — по ранее согласованному объёму. Интернет-оплата, доставка, рейтинги, карта, календарь записи и push-уведомления не входят в первую версию. Деньги и вещи передают при встрече. Отсутствие модерации — ограничение учебного MVP, а не готовая модель публичного маркетплейса.

Регистрация доступна пользователю с электронной почтой; вуз выбирается из справочника, общежитие — из существующих значений либо вводится пользователем. Такой выбор сам по себе НЕ подтверждает, что человек действительно студент. Проверка статуса студента — отдельная будущая функция.

## 2. Что проверено в Figma

[Исходный файл «Рядом — Mobile MVP»](https://www.figma.com/design/Il1x1YL5rRDL3cPNb2tquG/?node-id=0-1). Название файла старое, на экранах уже «Общажный ЧР».

На странице Foundations найдено 19 верхнеуровневых экранных фреймов: 8 базовых сценариев, их старые копии и варианты состояния главной/профиля. Основной набор с переходами — узлы `25:*`; варианты фильтров/профиля — `36:*`. Это не 19 отдельных экранов приложения.

|---|---|---|
| Вход | `25:12` | Email, пароль, проверка полей, сохранение сессии |
| Регистрация | `25:31` | Имя, email, пароль, вуз и общежитие |
| Главная | `25:55` | Лента, поиск, фильтры, нижняя навигация |
| Объявление | `25:106` | Модальное представление подробностей, автор, действия |
| Список чатов | `25:138` | Диалоги, последнее сообщение, непрочитанные |
| Переписка | `25:169` | История, настоящее поле ввода, отправка, карточка сделки |
| Профиль | `25:195` | Свои объявления, добавление, редактирование профиля и выход |
| Добавление объявления | `25:236` | Фото, название, описание, категория, тип, место |

Наблюдения, которые нужно учесть при переносе в код:

- На главной элемент «Чаты» (`25:275`) ведёт сразу в переписку, а «Профиль» (`25:276`) — в создание объявления. В приложении они должны открывать список чатов и профиль соответственно.
- «Забронировать» в подробностях сейчас ведёт на главную. Переход в макете не означает, что бронь действительно сохраняется.
- В форме объявления есть выбор формата передачи, но нет поля цены. Для продажи и услуг оно необходимо.
- На главной есть варианты фильтров «Все / Отдам / Обмен». В приложении добавляем «Продам / Услуга», а категории «Книги / Техника / Одежда / …» держим отдельным фильтром.
- Варианты главной и профиля становятся состояниями одного экрана, а не отдельными маршрутами.
- Расстояния в метрах — демонстрационные подписи. В MVP показываем общежитие/место; реальные расстояния потребуют координат и отдельной реализации.

Макет в ходе этого архитектурного обследования не изменялся. Навык figma-use использован для чтения структуры, переходов и визуальной проверки главной и формы.

## 3. Дополнения к экранному составу

Отдельный экран «Мои сделки» исключён по запросу пользователя. Состояние вещи и действия автора доступны в объявлении и связанной переписке; отдельный блок бронирований в профиле не нужен.

Дополнительные служебные формы:

- Редактирование объявления — та же форма, что при создании, с заполненными данными.
- Редактирование профиля — имя и общежитие; выход из аккаунта в профиле.
- Восстановление пароля, подтверждение почты и установка нового пароля. Для запуска через Expo Go предлагаем ввод одноразового кода из письма прямо в приложении, без обязательных собственных deep links. Потребуется почтовая отправка на backend; код ограничен по сроку, числу попыток и повторной выдаче.

Каждый экран предусматривает загрузку, пустое состояние, ошибку и повтор запроса. Формы показывают ошибки рядом с полями и защищают от повторной отправки. Для недоступного объявления предусмотрено отдельное состояние, а не падение приложения.

## 4. Технологии и разделение ответственности

| Часть | Выбор | Назначение |
|---|---|---|
| Мобильный клиент | React Native + Expo + TypeScript | Интерфейс и взаимодействие с Android |
| Навигация | Expo Router | Группы авторизации, вкладки, страницы и модальные маршруты |
| Серверные данные на клиенте | TanStack Query | Запросы, кеш, загрузка, повторное получение и обновление списков |
| Формы | React Hook Form + Zod | Состояние полей и проверка введённых данных |
| Оформление | StyleSheet и общая тема | Цвета, отступы, типографика и компоненты по Figma |
| Серверная часть | Python + FastAPI | HTTP API, авторизация, права, бизнес-логика, WebSocket чата |
| База данных | PostgreSQL на сервере пользователя | Постоянное хранение данных, ограничения и транзакции |
| Работа с БД | SQLAlchemy + Alembic | Запросы из Python и версионированные миграции схемы |
| Фото | Expo ImagePicker | Выбор фотографий с телефона |
| Сессия на устройстве | Адаптер Expo SecureStore | Защищённое сохранение токенов, без сохранения пароля |

Сервер принадлежит пользователю; отдельный SaaS-backend не используем. Для схемы размещения предлагаем reverse proxy (Caddy либо уже имеющийся Nginx), FastAPI/Uvicorn, PostgreSQL и постоянный каталог фотографий. Конкретный домен, ОС сервера и существующие сервисы уточняем перед развёртыванием, ничего на сервере сейчас не меняем.

Базовая связь: Android-клиент → HTTPS-домен → reverse proxy → FastAPI → PostgreSQL и файлы. Условный адрес API: `https://api.example.com/api/v1` — это пример, не назначенный пользователю домен. DNS указывает на публичный IP сервера; TLS-сертификат обеспечивает HTTPS. Изменения чата приходят по WSS. PostgreSQL доступен только backend по внутренней сети/localhost, порт 5432 в интернет не публикуем.

Сервер отвечает за доступ к данным, обязательные проверки, создание диалогов, переходы статусов и атомарное резервирование. Клиент показывает результат и проверяет поля для удобства, но не считается доверенным источником разрешений.

Операции выполняются Python-сервисами в транзакциях PostgreSQL. FastAPI принимает и проверяет HTTP-запрос, сервис проверяет права и правила, слой работы с БД сохраняет результат. Транзакция принадлежит бизнес-операции, не каждому отдельному запросу. На клиенте типы API генерируем из OpenAPI, а не раскрываем внутренние модели базы.

Для эксплуатации предусматриваем отдельные тестовую и рабочую базы, серверные секреты, резервное копирование БД И фотографий за пределы этого сервера с проверкой восстановления, логи без токенов/паролей, healthcheck и перезапуск процесса. Docker Compose возможен для воспроизводимого запуска, но это не обязательное пользовательское требование.

Expo Router использует файловую навигацию; обычные компоненты не размещаем в папке маршрутов. [Документация Expo Router](https://docs.expo.dev/router/basics/core-concepts/).

[HTTPS перед FastAPI](https://fastapi.tiangolo.com/deployment/https/), [WebSocket в FastAPI](https://fastapi.tiangolo.com/advanced/websockets/). Expo Go не заменяет backend и может обращаться к нашему HTTPS API.

## 5. Навигация

После старта восстанавливаем сессию. Пока проверка не завершена, показываем загрузочный экран. Без сессии доступны вход/регистрация/восстановление. После входа — три вкладки: «Главная», «Чаты», «Профиль».

- Главная → объявление → написать автору → переписка.
- Объявление → отправить заявку → переписка с карточкой заявки.
- Чаты → выбранная переписка → связанное объявление.
- Профиль → добавить/редактировать объявление → успешное сохранение → профиль с обновлённым списком.
- Чаты → переписка → управление статусом своего объявления.

Подробности объявления оформляем модально, как в Figma, но у них есть собственный маршрут с ID. Идентификатор передаётся в маршрут, данные загружаются из API. Один экран обслуживает все объявления.

Android Back закрывает модальное окно или возвращает на предыдущий экран. В чате клавиатура не закрывает поле ввода. При уходе из изменённой формы спрашиваем, нужно ли отбросить изменения. Безопасные области и размер шрифта учитываем; экран не привязываем жёстко к 390×844.

В каждом feature создаём `screens`, `components`, `api`, `hooks`, `schemas` и `types` по необходимости, а не набор пустых папок. Маршрут подключает экран из feature; экран не содержит SQL и не управляет низкоуровневой подпиской напрямую.

Зависимости идут от маршрутов к features, от features к shared. Shared не импортирует features. Например, `chat` может использовать публичный `DealPanel` из `deals`; обратной зависимости не создаём. Общие типы ответов берём из OpenAPI-контракта FastAPI. Модель таблицы и публичная схема ответа различаются: хеш пароля и другие приватные поля не выдаются клиенту.

Обычное локальное состояние — React; формы — React Hook Form; данные сервера — TanStack Query; текущая сессия — AuthProvider. Redux и отдельный глобальный store для MVP не требуются. [TanStack Query для React Native](https://tanstack.com/query/latest/docs/framework/react/react-native).

| `listings` | Автор, тип, категория, название, описание, статус, общежитие, цена |
| `listing_photos` | Объявление, ключ файла в серверном хранилище, порядок фотографий |
| `conversations` | Объявление, автор, заинтересованный пользователь, отметки прочтения каждого участника |
| `messages` | Диалог, отправитель, текст, серверное время, ID для защиты от дублей |
| `deals` | Диалог, заявка, статус, снимок типа/условий/цены, даты изменения |

Связи: вуз содержит общежития; пользователь публикует много объявлений; у объявления много фотографий и диалогов; в каждом диалоге ровно два участника и много сообщений; сделки принадлежат диалогу. Услугу тоже хранит `listings`, отдельная дублирующая таблица услуг не нужна.

ID — UUID. Деньги — целое количество копеек, валюта MVP — RUB. Не используем дробное число для хранения суммы. Время хранится на сервере с часовым поясом и отображается локально. Фото хранятся в постоянном каталоге на сервере вне исходного кода, в PostgreSQL — ключи файлов и метаданные. Интерфейс файлового хранилища позволяет позже перейти на S3-совместимый сервис, если это потребуется.

Вуз пользователя выводится через его общежитие. Выбранный вуз в форме ограничивает список общежитий. Университет не дублируем в нескольких несогласованных полях.

`listings.type`: `sale | giveaway | exchange | service`.
`listings.status`: `draft | active | reserved | completed | archived`.
Тип отвечает на вопрос «что предлагают», статус — «доступно ли это сейчас».

## 8. Четыре типа объявления

| Тип | Дополнительные поля формы | Действие пользователя |
|---|---|---|
| Продам | Цена больше нуля | Написать / запросить бронь |
| Отдам | Цена отсутствует, отображаем «Бесплатно» | Написать / запросить бронь |
| Обмен | Детали в общем описании | Написать / предложить обмен текстом |
| Услуга | Описание результата, фиксированная цена или «Договорная» | Написать / заказать |

Для обмена в MVP предложение описывается текстом, без автоматического обмена двумя связанными объявлениями. Для услуги время и место обсуждаются в чате; полноценного календаря слотов нет.

Обязательные поля API: название, описание, категория, формат и цена с правилами для выбранного формата. Место встречи обсуждается в чате. Публикация без фото допустима, предел — пять. Ограничения размера/типа файла задаются и на сервере. Поле «Добавить вещь» переименовываем в «Добавить объявление», чтобы оно подходило услугам.

## 9. Заявки, бронирование и завершение

Термины: «владелец» означает автора объявления — продавца/человека, отдающего вещь, либо исполнителя услуги. Это НЕ администратор приложения и НЕ владелец сервера. Один пользователь выступает автором своих объявлений и покупателем в чужих.

Независимое обязательное правило доступа: покупатель не может редактировать, удалить или самостоятельно пометить чужую вещь проданной. Автор управляет своим объявлением; backend проверяет авторство.

Следующий сценарий подтверждения брони — предложение ассистента, пока не согласованное пользователем. Оно дополнительно защищает от блокировки чужих объявлений простым нажатием «Забронировать». Не реализовывать эту бизнес-логику как утверждённую до выбора пользователя. Альтернативы: автоматическая бронь на ограниченный срок либо ручная отметка автором после договорённости в чате.

1. Пользователь отправляет заявку. Сервер проверяет объявление, запрещает заявку на своё, создаёт или возвращает диалог и записывает `pending`.
2. Владелец принимает заявку (`accepted`) или отклоняет (`declined`). До принятия вещь ещё не зарезервирована.
3. Для продажи, передачи и обмена принятие переводит объявление в `reserved`. Остальные ожидающие заявки на эту вещь отклоняются с понятной причиной.
4. После передачи владелец завершает сделку (`completed`), вещь становится `completed` и исчезает из активной ленты.
5. Заказ услуги не резервирует объявление целиком: исполнитель может принять несколько заказов от разных людей. Завершение одного заказа не снимает услугу с публикации.
6. Клиент отменяет свою ожидающую заявку; принятую сделку может отменить любой её участник. Статус — `cancelled`, зарезервированная вещь снова `active`. Завершённые сделки повторно не отменяются.

Переходы: `pending → accepted / declined / cancelled`; `accepted → completed / cancelled`. Произвольные изменения статуса запрещены сервером. При активной сделке нельзя менять тип и существенные ценовые условия объявления; согласованные условия сохраняются в сделке.

Для резервирования Python-сервис блокирует строку объявления и проверяет актуальное состояние внутри транзакции PostgreSQL. Для вещевых сделок нужен уникальный индекс на принятую резервирующую сделку по `listing_id`. Признак того, что сделка резервирует вещь, вычисляется сервером из типа объявления, а не принимается на доверии от телефона.

Дополнительно: один диалог на пару «объявление + заинтересованный пользователь», одна незавершённая заявка на диалог, идемпотентное повторение действий. Если два человека одновременно пытаются получить вещь, сервер не допускает двух подтверждённых броней.

Предполагаемые HTTP-группы под `/api/v1`: `/auth`, `/users/me`, `/universities`, `/dormitories`, `/categories`, `/listings`, `/conversations`, `/messages`, `/deals`. Изменение сделки — отдельные действия, например `POST /deals/{id}/accept`, а не произвольная запись статуса. Точный контракт сделок фиксируется после согласования сценария брони. Эти операции проверяют инициатора, доступ и состояние; клиент не записывает итоговый статус напрямую.

## 10. Лента, чат и фотографии

Лента: активные объявления, выбранный вуз/общежитие, сортировка по дате, независимые фильтры типа и категории, поиск по названию/описанию. Используем постраничную загрузку и стабильный порядок по дате и ID; поиск — с небольшой задержкой после ввода и параметризованным серверным запросом.

На старте «рядом» означает выбранное общежитие или вуз, а не GPS-радиус. Геолокацию не запрашиваем. «Зарезервировано» видно владельцу, участникам сделки и при открытии уже известной карточки; такие вещи не включаем в обычную ленту доступного.

Чат: отправка и история через HTTP API; после фиксации сообщения в БД FastAPI сообщает о нём участникам через WebSocket (WSS). История запрашивается постранично. После восстановления сети или возврата в приложение получаем пропущенные сообщения заново: WebSocket не заменяет постоянное хранение. У отправки есть состояния «отправляется / отправлено / ошибка» и повтор с тем же ID, без дублирования.

На старте один процесс FastAPI может держать соединения в памяти. Если запускаем несколько workers или экземпляров, нужен общий механизм доставки событий (например, Redis Pub/Sub); нельзя рассчитывать, что словарь соединений разделяется между процессами. Потеря события компенсируется получением истории; сообщения подтверждаются только после сохранения в PostgreSQL.

Отметку прочтения каждый участник может менять только для себя. На выходе из диалога снимаем ненужную подписку; на выходе из аккаунта — все приватные подписки и кеш. Push и онлайн-статус не нужны для первой работающей переписки.

Публикация с фотографиями: создать закрытый draft → загрузить файлы в разрешённый путь пользователя/объявления → записать метаданные → сервером проверить комплектность и опубликовать. При ошибке остаётся draft для повтора, а не активное объявление с потерянными фото. Неиспользованные загрузки предусматриваем к очистке.

MVP работает онлайн. Без сети разрешено показать уже полученные данные с предупреждением, но нельзя показывать успешную публикацию, сообщение или бронь, пока сервер не подтвердил операцию. Полноценной офлайн-синхронизации нет.

## 11. Безопасность

- FastAPI проверяет пользователя и доступ к каждому объекту: изменение объявления только автором; диалоги, сообщения и сделки только участникам. Проверки действуют для HTTP и WebSocket. Клиенту прямой доступ к таблицам не выдаётся.
- Email и служебные поля пользователя не публикуются в профиле автора. Номер комнаты не делаем обязательным публичным полем; точное место встречи можно сообщить в чате.
- Учётную запись инициатора получаем из проверенного access-токена, не из доверенного на слово `user_id` в запросе. Схемы изменения перечисляют разрешённые поля и запрещают подстановку автора/статуса. Пароли хешируем Argon2id. Вход выдаёт один JWT с настраиваемым сроком; выход удаляет его на устройстве, после истечения нужен повторный вход. Токены в БД не хранятся.
- Пароли БД, ключ подписи токенов и почтовые секреты хранятся только на сервере. `EXPO_PUBLIC_API_URL` содержит публичный адрес API, не секреты. Для FastAPI используем отдельную роль БД с минимальными правами; миграции — отдельно.
- HTTPS/WSS обязательны для внешнего доступа. PostgreSQL закрыт от интернета. Авторизация, коды подтверждения и загрузки защищаются ограничениями частоты/размера; долгоживущие токены не помещаем в URL и журналы.
- Пароль не сохраняем на устройстве. Хранилище сессии реализуем адаптером SecureStore с обработкой ошибок/размера значений; не логируем токены. При выходе удаляем сессию и приватный кеш.
- Проверки формы дублируются Pydantic, сервисной логикой и ограничениями PostgreSQL. Загрузки проверяются по реальному содержимому, формату и размеру; сервер генерирует безопасные имена файлов. Закрытые файлы выдаются через проверяющий доступ endpoint, а не публичным листингом каталога.

[Авторизация и хеширование в FastAPI](https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/), [SecureStore на Android](https://docs.expo.dev/versions/latest/sdk/securestore/).

## 12. Разработка и показ на Android

На компьютере обнаружены Node.js `22.15.0`, npm `10.9.2` и Git `2.47.0.windows.1`. Перед созданием приложения проверяем требования выбранного Expo SDK и при необходимости обновляем Node до подходящего поддерживаемого LTS; установленные версии ещё не означают проверенную совместимость.

Для первого запуска пользователь устанавливает Expo Go на Android. Мы создаём совместимый с установленным Expo Go проект и запускаем `npx expo start`; телефон сканирует QR-код и исполняет приложение. Это не трансляция экрана компьютера. Обычно устройства находятся в одной сети; если сеть общежития изолирует устройства, пробуем tunnel. [Запуск Expo](https://docs.expo.dev/get-started/start-developing/).

Expo — инструменты и библиотеки для разработки React Native. Expo Go — установленная на телефоне среда запуска нашего проекта во время разработки. Expo Router — библиотека внутри исходного кода, отвечающая за экраны, вкладки и кнопку «Назад»; отдельно на телефон её не устанавливают. Все три работают совместно, это не альтернативы друг другу.

При разработке есть две независимые связи: компьютер отдаёт код приложения в Expo Go, а приложение на телефоне обращается за данными к FastAPI по публичному домену. Серверу FastAPI не нужно находиться в одной Wi-Fi-сети с телефоном. Expo не размещает нашу базу и не заменяет API.

Expo Go — целевой способ первоначальной проверки всех основных сценариев MVP. Подбираем совместимые библиотеки. Development build понадобится только при выходе за его нативные возможности; это не обязательный первый шаг. Позже собираем отдельный Android APK для установки и демонстрации без работающего компьютера. AAB понадобится при публикации через магазин. [Среда разработки Expo](https://docs.expo.dev/get-started/set-up-your-environment/).

Android Studio, эмулятор и Java не обязательны для старта на физическом Android через Expo Go. Для backend нужны Python и отдельная среда зависимостей; для серверных интеграционных тестов — отдельная тестовая PostgreSQL локально или на сервере. Рабочую БД для тестов не используем. Для облачной сборки APK впоследствии может понадобиться аккаунт Expo, но не аккаунт облачного провайдера БД.

После установки самостоятельной сборки приложение обращается к общему серверу по интернету: у пользователей разные аккаунты, но общие объявления и переписки с правами доступа. Сам факт серверной БД не распространяет приложение — APK или публикация в магазине организуются отдельно.

## 13. Порядок реализации и проверка

1. Создать Expo-проект, зафиксировать совместимые зависимости, подключить тему, навигацию и проверить старт на телефоне.
2. Собрать 8 экранных сценариев по Figma на явно демонстрационных данных: настоящие поля ввода, dropdown, поиск/фильтры, состояния форм. Исправить направления переходов при реализации.
3. Создать FastAPI backend, модели SQLAlchemy, миграции Alembic, проверки доступа и отдельную тестовую базу. Подключить регистрацию, вход, сессию и профиль. Развернуть тестовый API на сервере через HTTPS-домен после уточнения доступа и окружения.
4. Реализовать сквозной сценарий: пользователь A публикует объявление с фото, пользователь B видит его на своём устройстве, находит поиском и открывает подробности.
5. Подключить реальные диалоги, отправку сообщений, непрочитанные и восстановление после обрыва связи.
6. Согласовать способ бронирования и выбранные серверные переходы статусов в объявлении/чате; отдельно проверить продажу, передачу, обмен и услугу.
7. Проверить восстановление пароля по коду, ошибки сети, работу клавиатуры/Back; собрать устанавливаемый APK.

Критерии готовности MVP:

- Два аккаунта видят общие опубликованные данные и получают сообщения друг друга.
- Данные сохраняются после перезапуска; после выхода нельзя открыть чужую приватную историю через кеш или прямой маршрут.
- Пользователь не может изменить чужое объявление или прочитать чужой диалог через API.
- Две конкурентные операции не создают две подтверждённые брони одной вещи.
- Заказ услуги не скрывает её от других клиентов; завершение сделки с вещью убирает её из активной ленты.
- Форма проверяет поля в зависимости от типа; фотографии корректно загружаются и повторяются после ошибки без дублей.
- В standalone APK нет зависимости от запущенного Expo dev-сервера; для серверных функций нужен интернет.

Автоматизация проверок: типизация и lint; тесты схем форм и согласованных переходов статусов; тесты компонентов критических форм; Pytest-тесты API, доступа к чужим объектам, авторизации WebSocket и конкурентного бронирования на настоящем PostgreSQL. Финальная проверка — на физическом Android и двух пользовательских сессиях.
